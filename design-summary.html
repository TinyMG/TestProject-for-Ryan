Workflow Design Summary: Financial Template Web App Builder

Each run researches one sample financial-template URL from the web and regenerates a local, double-click-to-open web app of business-plan financials, an operating budget, and a one-page decision dashboard — pre-filled with Miralles Music Academy's real numbers.

2Structure — 1 skill, flow, and freedom

Skill: building-financial-template-app
Researches a sample financial template online, then builds a consistent local web app for Miralles Music Academy. One skill — the research brief is the internal seam that keeps scraped web content out of the build context.
1 · Research sample URLHigh → Med
Browsing is free-form (every URL differs), but output is fixed-shape: open the sample URL in the headless browser, extract sections / line items / metrics / layout ideas; re-verify live tuition on mirallesmusic.com; gather CAD music-school benchmarks. Reads school-profile.md, references/benchmarks.md, references/learnings.md. Uses assets/research-brief-template.md.
research-brief.md
STOP — Checkpoint 1
Owner reviews the brief: what will be adopted as-is vs. adapted for a music school, and the proposed default numbers. Approve or redirect before any code is written. Co-review.
2 · Generate the web appMedium
Fill the assets/app-scaffold/ (HTML shell, 3 tabs, editable fields, localStorage machinery) using ONLY the brief + school profile — never half-remembered scraped pages. One shared numbers model drives all tabs (inferred). Tab 3 is a decision dashboard: margin, break-even enrollment, what-if levers, teacher capacity (90 students / 6 teachers) (inferred).
app files in project folder
3 · VerifyLow
Exact checklist: headless browser load → zero console errors → click every tab → no blank number fields → recompute totals from the numbers model → cross-check break-even vs. P&L → screenshot each tab.
verification note + tab screenshots
STOP — Checkpoint 2
Owner reviews screenshots and the verification note. Approve, or send corrections back to Phase 2. Approve. Run then ends by updating references/learnings.md.

research-brief.md (internal seam within one skill)
Build context (same run)
Why the brief exists as an artifact: Phase 2 builds only from the brief + profile, so the volume of scraped web content never pollutes the context that writes the app. If runs ever feel bloated, split into a research skill + build skill using the brief as the formal handoff.
Consistency guaranteeMedium
Because every run regenerates the full app, the scaffold keeps look & behavior identical run to run — only content changes. Owners' edits live in localStorage, not in the scaffold.
High freedom — prose/heuristics Medium — template-driven Low — strict template / exact steps STOP — checkpoint (human in the loop) OUT: output artifact
Determinism: no scripts/ — deterministic behavior comes from the fixed app scaffold (assets/) and the exact verify checklist. The heavy lifting (page scraping, rendering) happens through the browser tools, which are already deterministic executors.

4Alignment — struggle points and checkpoints

Copying the sample template verbatim instead of adapting it to a music school
fixed by
Mandatory "adopt vs. adapt" table in every research brief
Forces explicit judgment for each borrowed section before Checkpoint 1, where the owner sees it.
Tabs disagreeing with each other — break-even says one thing, P&L another, budget a third
fixed by
Single numbers model: one JS data object all three tabs render from
No hardcoded numbers in tab markup; verify step recomputes from the model.
Stale pricing — tuition tiers change but the app keeps old rates
fixed by
Profile stores the school URL; Phase 1 re-verifies live pricing each run
Real rates ($160/$230/$300 L1, $199/$285/$365 L2, $50 reg fee, bi-annual −7% / annual −14%) always come from the live site.
Research phase burying the build phase in scraped web content
fixed by
research-brief.md as a hard context seam inside one skill
Phase 2's rule is literal: build only from the brief + profile, never from memory of the pages.
Checkpoints: two. Checkpoint 1 after the brief — plan approval, co-review with the owner (cheapest point to fix a misread of the sample). Checkpoint 2 after verification — owner reviews screenshots + verification note and approves or sends corrections back to Phase 2.
